# 本地技能工具

`kochab` 命令行是技能文件夹的版本化工具：在 Git 之上的一层薄封装。技能文件夹本身就是候选——你用自己的文件工具直接读取和修改它，`kochab` 只负责快照、对比、采纳与回滚。整轮调优由编程智能体主导；程序不调用模型、不内置评测器，也不观测执行。

## 谁来执行任务

任务要交给独立的执行者运行。执行者的行为必须来自技能本身，而不是来自你会话里已有的上下文——否则你读到的是被你修正过的结果，验证不成立。按顺序确认你的手段：

1. 能派 sub agent：交给 sub agent；
2. 能给自己开新会话（再启动一个智能体实例、新开一个任务）：交给那个会话；
3. 都不能：向用户说明，请用户开一个干净的会话执行任务并带回输出，你继续负责分析、修改与结算。

无论哪种方式，执行者在开始任务时都不应带有本轮调优的上下文。执行记录也从派发它的通道带回来：sub agent 的 transcript、会话的输出，或执行者写下的文件；`kochab` 不接收轨迹。

## 开始调优

确定目标 skill 和期望改善的任务效果，优先从用户提供的失败、反馈或实际任务入手。只有影响调优方向的信息不明确时才继续澄清。

需要 Python 3.10+ 和 Git。若 `kochab --help` 不可用，在你使用的 Python 环境中执行：

```sh
python -m pip install -e "<本技能所在的 Kochab 仓库目录>"
```

```sh
kochab init <目标技能文件夹>
```

初始化可重复执行以继续已有工作。返回的 `candidate` 是当前内容标识，`accepted` 是已采纳版本，`changed` 表示是否有未采纳的改动。技能文件夹内的常规文件进入版本；隐藏文件、缓存、构建目录和依赖目录不进入版本，链接文件不受支持，根目录 `SKILL.md` 必须保留。

## 真实任务

每一轮都要在真实任务上运行：用户指定的，或你依据 skill 的适用场景设计的。真实任务是做完真有交付、结果可以检验的任务；玩具任务只会奖励玩具改动。

任务会被运行改变。把任务拷贝成若干份，每次执行用一份，运行前初始化到任务的初始状态，用过的副本不复用。两次运行要可比，前提是两次都从同一起点开始。

## 一轮闭环

**准备。** `kochab init`（继续已有工作时再次执行即可）确认状态，直接阅读技能内容，确定这一轮要改善什么；把真实任务拷贝成若干份并初始化。

**执行。** 把技能交给执行者——给它一句话：阅读 `<技能文件夹>` 内的 `SKILL.md`，在其中一份任务副本上完成任务。执行记录从派发它的通道带回来。

**分析。** 你来读证据：执行记录、任务结果、用户反馈，自然语言观察也可以作为判断依据。判断失败发生在哪一步，证据指向技能的哪一部分。

**修改。** 用你自己的文件工具直接修改技能文件夹；`kochab diff` 查看相对已采纳版本的改动。

**复测。** 让下一个执行者在另一份初始化的任务副本上再次运行，对照两次效果。

**结算。** 有充分依据保留时：

```sh
kochab accept <目标技能文件夹>
```

效果不满意时用 `kochab rollback` 放弃本轮改动，技能文件夹还原为已采纳版本。证据不足时继续观察或修改。按任务需要迭代，直到改善得到验证或需要用户决定新的取舍。

## 命令

除 `diff` 外，成功结果输出 JSON。失败退出码非零。

| 命令 | 用途 |
| --- | --- |
| `kochab init <host>` | 开始或继续版本化 |
| `kochab diff <host>` | 当前技能相对已采纳版本的差异 |
| `kochab accept <host>` | 把当前内容采纳为新版本 |
| `kochab rollback <host>` | 放弃本轮改动，还原已采纳版本 |
| `kochab export <host> --out <新目录>` | 导出已采纳的技能 |

`<host>` 始终使用目标技能文件夹路径。

## 交付

导出到目标技能文件夹之外的新目录。`skill/` 是可直接使用的已采纳技能；`changes.diff`、`manifest.json` 和 `journal.jsonl` 分别提供累计差异、版本清单和操作记录。

交付时说明解决了什么、验证了哪些任务、观察到什么结果，并引用适用证据。这份说明可以保存在导出目录的 `argument.md`，也可以直接交给用户。
