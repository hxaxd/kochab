# 迁移：把评测驱动开发接入你的系统

参考抽象可以整体迁入你的软件：领域模型给出对象之间的关系，接口给出要实现的边界，循环给出一轮迭代的形状。迁移就是让系统尽可能对齐这个范式，并补齐它缺的设施：先读参考，对齐数据结构，审计系统，写补齐计划，然后进入评测驱动开发。

## 先读什么

- 思想：[《智能体如何扩展大语言模型的能力边界》](reference/capability-cycle.md)——领域基础、运行框架、评测环境与真实使用如何构成一个循环。
- 数据结构：[model](../src/kochab/model/__init__.py)、[port](../src/kochab/port/__init__.py)、[loop.py](../src/kochab/loop.py)——迁移要对齐的全部定义。

## 对齐数据结构

`model/` 定义一轮调优中各对象的关系。迁移时把你的系统映射上去：

| 对象 | 承载什么 |
| --- | --- |
| `Task` | 目标，以及可恢复的初始状态（`initial_state`）和验证器（`verifier`） |
| `Benchmark` | 一组有代表性的任务 |
| `Candidate` | 一次待验证的修改 |
| `Evaluation` / `CaseResult` | 候选在基准上的结果：通过与否、反馈、轨迹 |
| `Attribution` / `Finding` | 失败定位、解释与证据 |
| `Outcome` | 候选、评测结果与保留判断 |

对象之间用 `Artifact.ref` 互相引用——文件、数据库记录或服务资源都可以，由你的系统决定。

`port/` 定义要实现的五类接口：

- `Environment`：`describe` 说明提供的能力，`restore` 恢复任务的初始状态，`observe` / `act` 提供观察与行动；
- `Harness`：`describe` 给出运行框架的说明，`inspect` 让修改者检查其内容；
- `Evaluator`：`run(candidate, benchmark)` 执行候选并返回 `Evaluation`；
- `Attributor`：`run(evaluation)` 从评测结果得出归因，驱动方在两轮之间调用；
- `Curator`：`grow(benchmark, evaluation)` 把失败案例还原成任务补入基准，驱动方在两轮之间调用。

`loop.py` 定义一轮迭代：`Context` 汇集基准、环境、运行框架、基线结果与归因；`Iteration.revise` 调查证据并产出候选；外部评测执行候选；`Iteration.decide` 判断保留。`revise` 与 `decide` 留给你的领域实现。

对齐有明确的边界：核心循环原样保留；业务一侧尽可能对齐就好，不是把原有代码改写成参考的模样。数据结构在边界上用 adapter 翻译，接口实现包住已有的设施，对原有业务代码保持尽可能少的侵入。

## 审计你的系统

评测驱动开发的完整链路是：需求 → 任务环境 + 评测集 + 验证器 → 执行与轨迹 → 错误归因 → 修改 → 复测 → 保留或放弃；失败案例还原成新任务，回流进评测集，链路由此闭合。逐项核对你的系统现在有什么：

| 环节 | 要具备 | 核对问题 |
| --- | --- | --- |
| 任务环境 | 可恢复的初始状态，观察与行动的接口 | 同一任务能否从同一起点反复运行？外部依赖能否控制？ |
| 评测集 | 有代表性、能随失败增长的任务集合 | 任务是否覆盖真实需求？初始状态与验证器是否明确？失败案例能否还原成新任务补入？ |
| 验证器 | 自动判断结果 | 完成与否是不是可检验的事实，而不是人的感觉？ |
| 可观测性 | 可调查的执行轨迹 | 上下文、动作、工具返回与结果是否被记录、可回看？ |
| 归因 | 失败能定位到层 | 失败能否落到知识、观察、方法、工具或验证标准之一？ |
| 修改与复测 | 运行框架可迭代 | 改动有没有版本可对照？修改后能否重跑原任务与回归任务？ |

## 进入评测驱动开发

链路就绪后，在你的领域里实现 `Iteration`，让循环转起来：

1. **`revise`：读证据，做调查。** 读验证标准、原始轨迹与归因；需要查证时，通过 `Environment` 的接口恢复初始条件、观察状态或尝试行动。归因用来提出有依据的改动，也允许进一步调查修正判断。
2. **按证据选择修改位置。** 运行框架可能包含提示、资料、工具实现、状态管理与流程。证据指向环境或验证标准时，把问题交回相应部分处理，不能靠修改框架迎合错误的判断标准。
3. **`decide`：复测并判断。** 候选交外部评测，在明确的初始条件下重新运行原任务与相关回归任务；对照实际效果决定保留、继续修改或放弃，并记录候选、证据与评测结果之间的联系。
4. **两轮之间：失败回流。** 失败案例交 `Curator` 还原成新任务补入基准，转为两类用例：完整任务的回归用例，检验原始需求是否达成；错误前缀的续跑用例，保留出错前的上下文，检验错误决策是否复发。下一轮在长出来的基准上继续。

归因也可能指向验证器、环境设施或模型本身，这些发现由对应的外部工作继续处理。

上线不是链路的终点：一个正确上线的系统必须支持失败回流，真实使用暴露的失败案例，同样要能还原成可重复运行的任务补入基准，让评测集随真实使用持续增长；不支持回流，评测集就停在上线那天，循环只转了一半。
