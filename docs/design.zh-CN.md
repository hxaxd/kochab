# kochab 设计文档

> **独立项目**，仓库即本目录，项目名 **kochab**（曾用工作名 evolver，下文一律用 kochab）。
>
> 本文档描述目标架构；各项能力的实际完成状态见 [`implementation-status.md`](implementation-status.md)。
>
> 文中「宿主」= 被调优的目标 Agent 系统（harness + 评估 + 观测三件套的持有者）。

---

## 0. 一句话定义

kochab 是一个**极简的、框架无关的 harness 自动调优 Agent**：

- **接入期**（Agent 驱动 + 人在环）：通过只读代码勘探，把宿主的「可改点」「评估口」「轨迹口」映射成绑定草案，人类确认后**冻结**；
- **进化期**（约束内自治）：模型在冻结边界内读取证据、诊断、修改已声明单元并重构；框架固定每轮起点、完整训练验证、隐藏门禁、事务化采纳与失败回滚。

它同时支持两种证据来源：**离线评估**（跑评测集）与**在线人类反馈**（生产轨迹中的用户反馈），即同时覆盖评估驱动调优与持续在线学习。

## 1. 设计哲学

1. **本体极简**。kochab 自己就是一个极简 Agent：一个「模型循环 + 工具」的核心循环，一屏读完；上下文压缩保留为正交钩子，不做多角色编排，不用框架逻辑替模型做决策。
2. **契约极小，其余皆适配器**。「与任何东西无关」不是靠没有接口实现的，而是靠**三个最小契约 + 通用适配器 + Agent 生成的绑定草案**实现的（§2）。非标准运行时通过宿主侧薄 runner 或 OTLP 转换器接入，而不是进入核心循环。
3. **接入期人在环，进化期模型自治**。人类在接入期审阅绑定、圈定边界；启动进化后接口层不可变，可变的只有调优面内容。最终进化包仍由宿主侧人类审阅和合入。
4. **宿主只读，交付为进化包**。kochab 不把候选直接写回宿主生产文件：接入期把调优面复制到**工作副本**，每轮从最后已采纳版本开始；最终交付物是**进化包**（§3.3）——目标状态 + diff + 论证 + 前后评估证据，由宿主侧的人决定如何合入。
5. **双信号同权**。离线评估分数与在线人类反馈是同一种东西——关于宿主行为质量的证据流。kochab 不区分「评估模式」和「在线学习模式」，只区分证据的来源与置信度。
6. **评估驱动开发 = 红 → 绿 → 重构**。对齐 TDD 的完整循环而非前两步：通过评估（绿灯）不是一轮的终点，**重构才是**——把为过绿灯而累积的 case 特定内容泛化、归纳、重新组织，同时保持绿灯。过拟合靠重构的泛化压力挤出，而不是靠检查器拦截（§4.2）。

## 2. 三大契约（接入期产物，启动后冻结）

契约以 Python Protocol 表述。当前版本提供 files + CLI + OTLP 通用适配器；接入期 Agent 生成并校验绑定草案，人类审阅后冻结。非标准宿主需要在宿主侧提供薄转换器。

### 2.1 TuningSurface —— 调优面（宿主哪里可以改）

```python
class TuningSurface(Protocol):
    def manifest(self) -> SurfaceManifest: ...
    # 声明所有可改单元：id、语义类别（§2.4 四类）、物理形态（文件/配置/目录）、
    # 约束（格式、大小、禁改区）、当前版本指纹

    def read(self, unit_id: str) -> str: ...
    def apply(self, change: Change) -> Version: ...      # 原子应用，返回新版本号
    def rollback(self, to: Version) -> None: ...
    def diff(self, a: Version, b: Version) -> str: ...
    def baseline(self) -> Version: ...
    def accepted(self) -> Version: ...
    def mark_accepted(self, version: Version) -> Version: ...
    def restore_accepted(self) -> Version: ...

```

关键设计：`manifest()` 是接入期最重要的产物——它把「这个宿主我们能改什么、怎么改」一次性声明清楚。四个语义类别（§2.4）如何映射到物理形态由 manifest 声明，kochab 据此把变更落到**这个宿主实际存在的东西**上。物理形态是宿主的事，不是 kochab 的事：可能是系统提示词片段、配置文件、工具定义、工作流描述、skills 目录，也可能以上全无、只剩一块提示词。**skills 不是前提。**

**作用对象是工作副本**：接入期把宿主调优面复制为 kochab 管理的独立 Git 仓库，`apply/rollback/diff` 全部作用于副本；原始调优文件不被候选覆盖。这提供可验证的版本回滚，也使 `EvalPort.run(surface_version)` 能在隔离物化的指定版本上运行评估。评测命令本身属于接入期审阅过的可信宿主代码。

### 2.2 EvalPort —— 评估口（宿主怎么被评）

```python
class EvalPort(Protocol):
    def suites(self) -> list[SuiteInfo]: ...             # 可用评测集、用例清单、评估方法描述
    def criteria(self) -> str: ...                       # 评价标准/rubric 全文
    def gold(self, case_id: str) -> str | None: ...      # 标准答案（若有）
    def run(self, case_ids: list[str], surface_version: Version,
            visibility: str = "train") -> EvalResult: ...
    # EvalResult：总分、宿主判定的 passed、metrics、逐用例
    # (score, passed, feedback, output, metrics)
```

`(score, feedback)` 双通道是硬要求（对齐 GEPA 一族的 metric 契约）：只有标量的评估口会砍掉 kochab 最重要的诊断信息源。`passed` 必须由宿主评估口给出或按冻结的 `pass_threshold` 计算，kochab 不把所有框架硬编码成 `score == 1.0`。`visibility=holdout` 会同时设置 `OTEL_SDK_DISABLED=true`，防止门禁评估进入模型可见的标准轨迹流。

### 2.3 TracePort —— 轨迹口（宿主实际发生了什么）

```python
class TracePort(Protocol):
    def query(self, filter: TraceFilter) -> list[TraceRef]: ...
    # filter 含：时间段、状态、人类反馈标记（👍/👎/原因）、自动标记（失败/超限/中断）
    def read(self, ref: TraceRef) -> Trace: ...
    # Trace：OTel trace/span id、父子关系、时间、状态、属性、事件、输入输出和反馈
    def subscribe(self, filter: TraceFilter) -> Iterator[TraceRef]: ...
```

外部标准采用 **OTLP/HTTP + OpenTelemetry GenAI Semantic Conventions**；同时识别基于 OTel 的 OpenInference 语义与 Braintrust 评分属性。GenAI Agent 约定目前仍是 development 稳定级，因此内部模型保留全部原始 attributes/events，不把未知属性丢掉。daemon 内置 OTLP JSON、gzip JSON 与 protobuf 接收端，并通过文件轨迹口与持久化游标轮询新证据；真正的异步流式订阅尚未实现。

### 2.4 四类调优对象（语义分类，不落代码）

| 类 | 含义 | 典型物理形态（由 manifest 决定，宿主没有就不造） |
|----|------|------|
| **知识** | 模型会误解/不知道的事实与口径（领域概念、平台约定、工具语义澄清） | 系统提示词片段、知识库条目、知识型 skill（若有） |
| **经验** | 从反馈中提炼的做法偏好（「这类请求先做 X 再做 Y 效果好」「用户讨厌 Z」） | 提示词中的策略段、经验型 skill（若有） |
| **工具** | 既有工具描述、实现文件或参数默认值 | manifest 已声明的工具定义文件/代码 |
| **流程** | 做一类任务的步骤编排 | 提示词里的步骤段、工作流配置、流程型 skill（若有） |

分类的作用：让 kochab 的诊断结论（「这是知识缺口」vs「这是流程问题」）与变更落点对应起来，避免把答案硬塞进常驻提示词这种退化解。知识与经验的区分（客观口径 vs 反馈偏好）由 kochab 判断，不需要契约层面强制。

**宿主有什么就改什么。** 推荐「以 skill 承载流程」只是对 *已经有 skills 的宿主* 的偏好，不是 kochab 的运行时要求，更不是要把 Late-Bound Skills 那套表示塞进每一个宿主。没有 skills 的 harness（一块系统提示词 + 若干工具）完全合法，接入期照样冻结、进化期照样改那块提示词和工具描述。

## 3. 生命周期

### 3.1 接入期（Onboarding，Agent 驱动 + 人在环）

接入本身是一场由 kochab 的 onboarding 模式主导的对话式工作流：

1. **勘探**：人类给 kochab 指出宿主仓库/文档/运行方式；kochab 阅读代码，主动提问（「可改的是哪些文件/配置？有没有 skills，没有就没有」「评估怎么跑、结果什么格式？」「轨迹存在哪、怎么查？」）。不要预设宿主有 skills。
2. **生成绑定草案**：只读发现 Agent 把宿主映射到内置的 files + CLI + OTLP 适配器，生成 `kochab-host.yaml` 草案；若宿主不能直接满足标准边界，就把所需的宿主侧薄转换器列为未决项，不在发现阶段写代码。onboarding 随后读完所有调优单元、跑完整训练集与隐藏基线、探测一条轨迹，证明三口真的工作。
3. **共定进化计划**：对话敲定——跑哪些评测集做基线、在线证据源有哪些、holdout 回归门禁圈定（§4.1）、进化包导出的粒度约定（§3.3）。
4. **人审与冻结**：人类审阅绑定与未决项 → 确认启动 → 绑定、调优源文件、评测依赖、准则与用例目录 hash 固化。**此后进化 Agent 的工具集中不再存在「修改绑定/修改评估框架/修改 harness 框架代码」的任何通路**——不是靠提示词约束，是靠工具集物理上没有这个能力。调优源文件确需换代时，`--reset-state` 会先备份旧状态，再从新源建立工作副本。

### 3.2 进化期（自治循环，红 → 绿 → 重构）

```
感知（读新轨迹 + 上轮评估）→ 诊断（失败模式归因到四类，＝红）
  → 假设与变更（apply 到工作副本）→ 验证（自选用例 + 冻结门禁 §4.1，＝绿）
  → 重构（泛化/归纳/重组已积累的调优内容，保持绿灯，§4.2）
  → 采纳（副本内 commit）或回滚 → 记录（进化日志）→ 循环
```

模型决定每轮读取哪些证据、修改哪些已声明单元、运行哪些训练用例以及何时重构。每轮固定从最后已采纳引用开始；采纳前必须完成当前候选的完整训练集和隐藏门禁。历史分支选择与模型自建检查点不属于当前版本。

自身状态 = 一个 `.kochab` 目录（进化日志、模型自记的工作笔记、冻结封印与独立 Git 工作副本）。只有调优面进入该 Git 仓库；运行状态不混入候选提交。

### 3.3 交付形态：进化包（Evolution Package）

kochab 从不直接触碰宿主生产系统。阶段性成果以**进化包**导出（`kochab export`）：

- **目标状态与 diff**：调优面应当被改造成什么样（相对接入期基线或上一个包）；
- **论证**：每项变更的动机（归因到哪些轨迹/评估证据）、四类归属、重构说明；
- **证据**：变更前后的评估分数对比（含冻结门禁通过记录）、关键轨迹引用。

进化包本质上是一个带完整论证的 PR，宿主侧的人审阅合入。合入节奏、是否部分采纳由宿主侧自由决定；kochab 下一轮从哪个基线继续（自己的副本头 or 宿主实际合入后的状态重新同步）由模型自行判断与声明。

## 4. 防退化与防过拟合

### 4.1 冻结回归门禁（防退化，已确认采纳）

接入期由人类圈定一个**最小 holdout 回归集**（如 10–20 个代表性用例）：进化期 kochab **不可见其内容、不可改、采纳前必须通过**（由冻结的门禁程序执行，不经 kochab 之手）。模型仍可自由决定「额外」验证多少——门禁是下限不是上限。它是冻结线的一部分，不是运行时配置。holdout 同时充当过拟合的客观探测器：train 分数涨而 holdout 不涨即是信号。

### 4.2 重构（防过拟合的主机制）

「拟不拟合」本质上是模糊的，不适合用检查器做二值判定。本框架的防过拟合机制对齐 TDD 的完整循环：**红 → 绿 → 重构**。绿灯可以靠 case 特定的内容达成（等价于测试驱动开发里为过测试写的硬编码），而重构阶段以「保持绿灯」为约束，对累积的调优内容做泛化、归纳、去重、重新组织——case 特定的死记内容在泛化压力下被挤出或升华为一般规则。

重构时的判断标准（意思，不是要落地的运行时）：

- 尽量沉淀「这类情景用这种做法」，而不是「这个用例的答案是 X」；
- 能进按需加载位置的，不要堆进常驻提示词——**前提是宿主真的有按需加载**（skills、RAG、playbook、分文件提示词，什么都行）；没有就把提示词本身写得更一般，仍然靠绿灯约束。

除门禁与重构外不再加行为检查器。预算控制属于未来可选扩展，当前版本只提供每轮最大步数。

### 4.3 与 Late-Bound Skills 的关系（参考，不吸收）

*Late-Bound Skills* 所讨论的 binder/executor/meta-workflow/realization 表示与 kochab 无关，不作为依赖或宿主契约。

只看它的意思：过早把「跨情景可复用的做法」和「只在某种情形下成立的知识」焊成同一份常驻文本，会导致上下文膨胀和跨情景干扰。重构阶段用这个意思当品味——能分开写就分开写，能晚一点再和当前任务对上号就晚一点。

明确不做：

- 不在 kochab 里实现延迟绑定运行时（没有 binder 会话、没有 realization 库、没有元工作流协议）；
- 不要求宿主有 skills；没有 skills 时，调优面就是提示词/工具/配置，延迟绑定无从谈起，也无需谈起；
- 即便宿主有 skills，默认也按宿主自己的 skill 格式读写，不把宿主 skills 改造成 LBS 那种拆法，除非接入期人类明确要求。

## 5. kochab 自身架构

```
kochab/
├── core/loop.py          # 核心循环（一屏读完：感知→思考→工具→循环）
├── core/tools.py         # 进化工具的执行与采纳约束
├── core/tool_schemas.py  # 提供给模型的工具协议
├── contracts/            # 三大契约的 Protocol 定义 + 内部统一轨迹/评估视图模型
├── discovery.py          # 只读 Agent 勘探并生成绑定草案
├── onboarding.py         # 三口演练、基线与冻结封印
├── daemon.py             # 标准轨迹游标与持续进化
├── otlp_receiver.py      # OTLP/HTTP JSON + protobuf 接收端
├── gate/                 # 冻结门禁：holdout 执行器（不在 kochab 工具集内）
├── adapters/             # files、CLI、评估解析、OTLP 解码与语义投影
└── cli.py                # kochab onboard / kochab run / kochab daemon / kochab export
```

- **语言**：Python（生态、与主流 LLM 框架同侧、不用 TS）。
- **形态**：库 + CLI。单进程即可运行；daemon 模式通过 OTLP 接收端和持久化游标轮询轨迹。不绑定具体部署形态，因为它对宿主只经三大契约交互。
- **模型接入**：OpenAI 兼容聊天补全接口；模型、地址与凭据由命令参数或环境变量提供。发现与进化使用同一个薄 harness，门禁完全在模型工具集外执行。
- **自举**：kochab 理论上可以把自己当宿主调优（它自己就有提示词与流程）。**初期明确不做**，避免无穷回归与门禁自指；架构上不排除（它对宿主的要求自己都满足）。

## 6. 生态与适配器

### 6.1 最低共同分母适配器（关键交付物）

**`files + CLI + OTLP` 适配器**：调优面 = 文件系统（提示词、配置、以及 *如果存在的* skills 都是文件，manifest 用一个 YAML 描述目录与约束）；评估口 = 一条参数数组形式的命令（不经 shell）+ `kochab/jsonl/promptfoo/junit/inspect` 结果解析器；轨迹口 = OTLP/HTTP 在线接收或 OTLP JSON/JSONL 文件。

这使提示词和配置已经文件化、评估已有命令入口、轨迹能输出 OTLP 的 harness 只需声明绑定，无需编写进程内插件。缺少其中某个边界时，集成工作被限制为宿主侧薄 runner 或轨迹转换器，而不是修改 kochab 核心。

### 6.2 参考宿主：toy-desk（已实现）

`examples/toy-desk` 提供一块系统提示词、确定性评测器、10 个训练用例、6 个隐藏用例和 OTLP GenAI 轨迹，用于验证发现、冻结、红→绿→重构、隐藏门禁、失败恢复、daemon 触发与进化包导出。它是可运行的最小参考，不代表生产集成已经完成。

### 6.3 观测生态适配优先级

1. **OTel GenAI / OpenInference**：已实现 OTLP/HTTP JSON、gzip JSON、protobuf 和文件读取；
2. Phoenix、LangSmith、MLflow、Braintrust 通过标准 OTLP fan-out 接入；
3. 非 OTel 自研轨迹存储需由宿主提供薄转换器输出 OTLP；只读发现会把缺失的转换列为未决项，不污染内部契约。

### 6.4 评估生态适配优先级

1. 「命令数组 + 原生 JSON/JSONL」通用适配；
2. Promptfoo v3 JSON、JUnit XML（pytest/DeepEval）、Inspect JSON/`.eval`；
3. DSPy、GEPA、Ragas、MLflow 等库式评估通过极薄 JSON/JSONL runner 接入，保留其原生运行时与评分器。

另：**GEPA/ACE 等固定算法优化器不是竞品，是潜在工具**——kochab 可在进化循环中把「对某个提示词单元做一轮 GEPA 搜索」作为一个工具调用（二期）。kochab 与它们的本质区别：它们是固定算法，kochab 是**用 Agent 现场设计进化过程**的元层。

### 6.5 工具合成（未来方向）

当前版本能修改宿主已经在 manifest 中声明的工具定义或实现文件，但不动态扩大 manifest。未来可在宿主明确允许时，把轨迹中的**重复性确定工作**抽象成新工具（实现代码 + ToolSpec），再走同一套训练验证、隐藏门禁、版本化与回滚。

## 7. 关键取舍的论证

### 7.1 为什么「契约 + 适配器」而不是「纯对话式零接口」

接入期 Agent 可以勘探不同宿主，但只有能够映射到固定契约的宿主才能进入进化期；否则每轮都要重新理解运行时，冻结也无从谈起。契约是冻结线的物质载体。

### 7.2 为什么不做 pi / DeepSeek harness 的插件

插件路线 = 进入宿主进程：受限于宿主语言（TS）、宿主运行位置（本地）、宿主生命周期（会话级），且每个 harness 写一遍。依赖反转后：kochab 站在外面，宿主零侵入，语言无关、位置无关（宿主在集群里跑、kochab 在任何地方跑），一个最低共同分母适配器覆盖整类极简 harness。代价是失去进程内实时干预能力——但调优本来就是回合制的离线/近线行为，不需要进程内。

### 7.3 与宿主「自进化对接点」的关系

宿主侧文档中预留的 `(score, feedback)` 契约、版本化轨迹、git 化调优面，正是从宿主视角对三大契约的镜像描述。一个设计良好的宿主让接入期趋近于零工作量，但 kochab 不依赖宿主的良好设计——那是适配器的工作。

### 7.4 为什么不把 Late-Bound Skills 做成 kochab 的子系统

LBS 解决的是「skill 库在演化时如何避免过早绑定」；kochab 解决的是「满足三契约边界的 harness 如何被一个外部 Agent 调优」。前者是一种 *可选的宿主内部表示*，后者是 *宿主外部的元层*。把前者做成后者的默认运行时，等于假设所有宿主都有（而且愿意改造成）skills。品味可以参考，机制不吸收。
